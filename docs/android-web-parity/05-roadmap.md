# 05 开发路线、任务包与阶段验收

## 1. 排期方法

已确认先采用里程碑与验收关卡路线，按依赖和退出条件安排开发。每阶段验收通过后进入下一阶段，具体日期不作为阶段启动前置条件。P1 结束后根据编辑器、终端、流恢复原型的实际工作量细化任务；后续需要日历排期时，再补充团队人数、可用工时与目标交付日期。

开发优先级由依赖确定，不表示删除后续范围。全部功能族均进入完整产品；阶段 APK 必须注明覆盖范围。

## 2. P0：基线、盘点与立项

前置：能够读取固定 Web 源码，并准备隔离的对照服务器和测试账号。

| 任务 | 交付物 | 验证 |
|---|---|---|
| P0-01 锁定项目身份与分发 | 应用名、applicationId、签名与渠道记录 | 可明确区分测试与正式构建 |
| P0-02 锁定 Web / 服务端基线 | commit、部署版本、数据快照、运行步骤 | 相同环境可重新进入全部目的地 |
| P0-03 逐页展开控件 | 完整复刻矩阵、字段、状态、权限与截图 | 每个导航和条件入口都有条目 |
| P0-04 展开接口契约 | 页面→调用→handler→DTO→副作用 | 每个写入都有读回验证 |
| P0-05 建测试数据与用户路径 | 小数据、长内容、并发与权限 fixture | 数据可重置且不混入私人数据 |
| P0-06 建视觉采样 | computed style、资源、字体、矩形、动效 | 320 / 390 / 430 / 768 / 1023 可复测 |
| P0-07 选择工具链 | JDK / AGP / Gradle / Kotlin / Compose BOM / SDK 精确版本 | 官方兼容关系和空白样例构建通过 |

退出条件：矩阵无未盘点目的地；HTTP / HTTPS、账号、数据和版本明确；关键能力缺口及原型标准完整。无测试服务器时仍可做静态契约与本地 fixture，但该阶段的运行部分保持未通过。

## 3. P1：高风险原型，先形成技术证据

原型建在新仓库的工作分支，成功结果整理后进入工程基础；避免建立一套与产品不同的样例架构。

| 关卡 | 开发内容 | 通过条件 |
|---|---|---|
| G1 认证与网络 | status、登录、pair、Cookie、图片、SSE、WS、退出 | HTTP / WS、HTTPS / WSS均完成真实往返；pair不重复；401不误退新登录 |
| G2 Markdown | 源码 / 富文本、图片、表格、选区、中文 IME、序列化 | 无编辑往返及修改后对照语料通过；实际支持全部基线节点 |
| G3 保存并发 | 本地草稿、按文件串行、revision、三方合并、冲突材料 | Web / App 并发案例、迟到回包和切文件通过 |
| G4 双流恢复 | UIMessage、35类 Game 事件、active、checkpoint、控制 | 跨包 / 重连 / 后台 / 进程恢复后身份和结果对应 |
| G5 原生终端 | ANSI / VT、WS、中文、全屏、Ctrl-C、resize、owner | 完整输入与屏幕结果对应；切页不删PTY；关闭释放 |
| G6 远程与共存 | 扩展允许 / 禁用、动态入口、双端终端 | 权限表现一致；双端操作不误删对方PTY或丢失会话内容 |

退出条件：每个关卡都有代码、fixture、原生录屏和真实往返结果。失败项列出节点 / 事件 / 操作，不能只写“待优化”。终端实测出现误删或内容丢失时G6不通过，须在现有边界内解决或取得明确的范围决定；记录限制本身不构成通过。影响整体原生路线的缺口在大规模页面开发前决定。

## 4. P2：工程基础与公共界面

建立单 Activity、AppContainer、环境配置、导航、共享顶栏、左右抽屉、浮层、DesignTokens、中英文、主题与字号。接入 Room / DataStore、错误模型、作用域与请求退休机制。完成公共控件的全部状态。

退出验证：登录后能进入完整导航；两个主题和中英文可切换；320px与横屏不遮挡；键盘、返回、手势、焦点有对照结果；配置变化不重复创建请求。

## 5. P3：第一条完整写作链路

实现：连接 → 登录 → 选择书籍 → 打开项目目录 → 选择章节 → 富文本编辑 → 切源码 → 引用选区 → 进入 Agent → 发送 → 工具结果 → 变更审阅 → 保存 → 读回 → 离开再进入 → 断线恢复。

同时完成文件标签、章节状态、图片 / 表格、自动保存、冲突处理、完整消息、审批、提问、停止 / 暂停 / 队列、版本入口。成功路径和失败路径一起开发。

退出验证：相同初始数据及确定性模拟流产生相同文件和状态；真实模型验证协议及生命周期，不比较随机生成文本的逐字相等。后台恢复不重复发送；保存与选区定位可复查。

## 6. P4：独立模块并行完成

公共接口、设计参数与恢复模型稳定后，按任务所有权并行开发。

| 工作流 | 内容 | 依赖 | 退出证据 |
|---|---|---|---|
| P4-A 游戏 | 创建、主角、配置、剧情、行动、状态、历史、分支、重生成、审批、暂停恢复 | P1 G4、P2公共UI | 全剧情与分支对照、SSE回放、实际快照 |
| P4-B 工作台 | 项目与主副会话、文件、嵌入编辑、审阅、终端、历史、导出 | P1 G3/G5、P3消息 | 多项目隔离、完整消息、PTY生命周期 |
| P4-C 共通资源 | lore、创作方案、书籍、版本、Skills、Agents | P2表单 / 列表、P3编辑 | 各类增删改查与重新读取 |
| P4-D 设置与运维页面 | 14个设置section、自动化、消息、资源 / 扩展、条件页面 | P1 G1/G6、P2公共UI | 权限、分层、时区、已读与受限行为 |

建议并行分工按上述工作流分配工程师 / 代理，各自负责功能目录和对应矩阵行；公共层由指定集成人维护。任务交接必须包含输入输出类型、错误、作用域和测试 fixture。共享文件的修改先协调，避免模块各建一套流、表单或导航。

单人开发时按 P4-A → P4-B → P4-C → P4-D 顺序推进，已形成高风险原型的能力优先落地。实际安排可按人员专长调整，退出条件保持一致。

## 7. P5：全量双端对照

按矩阵执行全部页面、控件、条件状态及请求副作用。先做320 / 390下的基础流程，扩大到430 / 768 / 1023、横屏、深浅主题、中英文、长内容、大字体与键盘组合。

视觉问题按公共 token / 组件 / 页面归因后修改，再只重跑受影响用例。状态问题追踪作用域、命令、revision、回包顺序和恢复边界。修复一个并发问题时增加能复现该问题的测试。

退出条件：矩阵所有行都有结论；无未解释差异；所有保存、审批、权限与恢复用例通过；只存在明确登记的平台差异。

## 8. P6：真机与发布候选

锁定构建、签名、版本和渠道。验证最低支持系统、主测试系统和较新系统；在真实手机验证输入法、系统返回、横屏、网络切换、后台与进程重建、上传下载、安装与重启。

交付签名 APK、SHA-256、依赖 / 许可证清单、复刻覆盖报告、双端差异报告、测试记录、已知限制及运行指南。商店 AAB 仅在选定渠道需要时构建。发布到外部渠道是独立最终动作。

退出条件：发布候选在目标设备的核心链路通过；APK与报告可追溯到同一 commit；后端源码没有本项目的修改提交。

## 9. 任务进入与完成定义

任务进入开发前需要：矩阵 ID、明确行为、已核对端点、原始初始数据、设计状态和通过标准。依赖不满足的任务先完成契约，不用临时猜测填空。

完成时需要：实现位置、双端操作结果、适当的自动测试、错误和权限验证、截图及差异结论。仅使用 mock 的功能标为“fixture验证”；真实服务器和真机状态分别登记。

## 10. 进度与变更管理

每次提交对应矩阵 ID。每日更新完成、进行中和阻塞项，给出具体证据。里程碑报告按页面、流程、协议和平台分别统计。

基线变更先列新增 / 删除 / 修改的行为与接口，再评估影响和工期，更新基线与矩阵。后端接口缺口先核对现有 Web 是否有相同远程能力，确认后登记受影响功能；不擅自修改后端满足客户端实现。
