# 06 开发、测试与交付指导

## 1. 新仓库初始化顺序

1. 在仓库记录应用名、applicationId、目标系统、签名归属、分发渠道和 Web 基线。
2. 用 P0 核对的 Android Studio / AGP 工具链建立 Kotlin、Compose、单 Activity 项目，最低 API 26。
3. 固定 Gradle Wrapper、JDK、Kotlin / Compose 插件和 BOM、SDK 与依赖版本，放入 Version Catalog；提交 wrapper 和所需构建文件。
4. 建立 `app` 内 package、资源语言、主题、网络配置、AppContainer 和最小首屏。
5. 加入 JVM 测试、Android instrumentation 测试与 CI；空白首屏构建、安装、启动通过后进入 P1。

工具版本从 [AGP 官方发布与兼容说明](https://developer.android.com/build/releases/gradle-plugin) 以及 [Compose BOM](https://developer.android.com/develop/ui/compose/bom) 核对。不使用未固定的 `+` 版本，也不把开发机全局 Gradle 当构建入口。

## 2. 本地开发入口

以下是实施阶段要运行的命令。本轮仅提供文档，尚未生成 Gradle 工程或执行这些构建。

PowerShell，在新 Android 仓库根目录执行：

```powershell
.\gradlew.bat --version
.\gradlew.bat :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
.\gradlew.bat :app:connectedDebugAndroidTest
.\gradlew.bat :app:assembleRelease
```

前两条用于已配置项目的工具链和主检查。instrumentation 命令需要明确的模拟器 / 设备；release命令需要对应签名配置。签名私钥和密码使用开发机 / CI 密钥存储，不提交仓库。

先检查相关进程、模拟器、端口及数据目录归属。测试使用隔离服务器与可重置账号，不启动或重启未知归属的服务。

## 3. 每个功能的实施循环

1. 读取矩阵行和固定基线，在手机 Web 重现对应成功、失败和权限状态。
2. 记录操作、请求、响应、revision / 命令身份、读回结果和界面变化。
3. 先实现最小可验证的状态转换或协议适配，再连接真实界面。
4. 页面具备真实状态和副作用后，执行相同初始数据的双端步骤。
5. 对必要的协议、并发、恢复和关键流程补测试；纯样式 / 可撤销低影响调整用对应视觉检查。
6. 测试通过后提交证据并更新矩阵。没有新问题时不重复扩大测试。

提交建议采用 `feature(scope): ...` / `fix(scope): ...` 等清楚英文描述。业务 PR 登记矩阵 ID、行为、验证环境、证据与限制，按一个可检查的用户流程拆 PR，避免一页只有静态壳却无法操作。P0、工程准备和规划任务关联对应任务 ID 或 ADR；纯文档维护登记规格章节与静态检查结果，遵循 `AGENTS.md` 的检查范围。

**最低测试设备（冻结）**

固定模拟器 Pixel 6 / API 33 / 8GB RAM；屏幕 1080×2400 / 120Hz；系统默认字体 + 中英文；IME Gboard。App 构建类型 debug；服务端 `http://192.168.2.102:18081`（0.6.3 @ 85ec97c）；本地局域网。真机最低档暂不冻结，待 P1 有真机后补登记。

**测量方法（冻结）**

- 指标起止点与单位：输入到可见（用户动作提交 → 首帧可见，ms）；帧时间（FrameTiming GPU 帧间隔，p50/p95/p99，ms）；峰值内存（Android Profiler，MB）；流延迟（事件接收 → 投影可见，ms）。
- 统计口径：每项 5 次，去掉最高/最低取中位数；预热 1 次不计；冷启动 / 热启动分别记录。
- 采样工具：Android Profiler、FrameTiming、自建埋点；证据路径 `docs/evidence/<matrix-id>/<device-and-config>/`。
- 剔除模型生成时间：生成 / 流式测量用固定网络重放（录制真实响应重放），不计模型首 token 等待。

P1 测量按冻结记录附原始结果、汇总值和逐项通过 / 未通过结论，包含最低设备的结果；数据、设备或方法变更时先记录原因和影响，再重测受影响关卡。仅做截断、跳过部件或降低重放速率以满足预算不构成全量能力通过。

## 6. 必跑的恢复与并发组合

| 场景 | 核对结果 |
|---|---|
| 发送前断网 | 输入保留，未显示已接受 |
| 可恢复命令的本地事务提交前立即终止进程 | 没有发出 HTTP；只恢复上一份已确认持久化的输入，不把未提交命令当成已发送 |
| 可恢复命令的本地事务提交后、HTTP 发送前立即终止进程 | 恢复同一 command_id、scope、输入快照及 submitting 状态；先核对 canonical，不自动重复发送 |
| HTTP 发送后、收到回执前立即终止进程 | 以持久记录的同一身份核对服务端结果；结果不明时保留未确认状态，不创建新 command 重发 |
| 已收到回执、操作绑定事务提交前立即终止进程 | 不把尚未提交的本地回执当作恢复事实；重新读取 canonical 补齐绑定，不重复执行命令 |
| 草稿事务提交前立即终止进程 | 恢复对应 DocumentKey 最近已确认提交的世代；未提交输入属于已登记窗口，不宣称已保存或已恢复 |
| 草稿事务提交后立即终止进程 | 恢复已确认提交的内容、baseRevision 和 editGeneration，再与服务端比较；不能回退到更早的本地版本 |
| 本地事务失败或回滚 | 可恢复命令不发送 HTTP；草稿不显示本地已保存，保留错误和未提交状态 |
| 服务端已接受但回包丢失 | 查询确认，不以新command重复发送 |
| 流中断后重连 | 正确task与checkpoint，无重复消息 |
| 重连第二次再断 | 重新读取canonical，不重复使用一次handoff |
| 在A会话发送后切到B | A回包不污染B；A可恢复 |
| 在A项目保存后切到B | 文件与revision始终对应A |
| 保存等待期间继续编辑 | 旧快照回执不清除新的dirty状态 |
| 多文件快速切换 | 每份草稿均落盘并按key保存 |
| Web与App编辑不同段落 | 合并结果对应基线 |
| Web与App编辑同一段落 | 自动保存暂停，冲突材料可访问 |
| 审批出现后旋转或进程重建 | 同一个ask，不自动同意或重复提交 |
| 退出后迟到回包 | 不重新恢复私有页面或凭证 |
| 终端后台断开后回前台 | 附接原会话或明确会话已结束 |
| 双客户端启动与关闭 | 不误删未知owner，并记录Web清理影响 |

这些边界用例必须实际终止应用进程，分别确认事务提交与网络发送是否发生；仅重建 Activity、模拟旋转或等待退出回调不构成替代。复原只使用已经成功提交的本地记录，后台 flush 只作补充；不能依赖 onDestroy 或其他清理回调保存未提交输入。当前仅规定用例，尚未执行。

## 7. 双端视觉与行为对照

每个场景先重置初始数据，执行 Web 一次，再重置后执行 Android 一次。对只读页面可使用相同快照同时读取。会产生不可重复外部副作用的操作使用隔离环境或确定性替身，禁止为对照重复运行真实自动化。

基础组合：所有主要页面在390宽、中英文、深浅主题下；所有布局族在320和1023边界；关键输入 / 抽屉 / 游戏 / 自动化页面增加430、768和844横屏。长文本、大字体与IME组合按受影响组件覆盖，记录采用的组合表。

逐步核对：控件可见状态与文本 → 点击 / 输入顺序 → 脱敏请求与身份 → 服务端读回 → 返回后的焦点和滚动。截图在相同内容区裁剪，保存两端原图、叠加 / 差异图及元素参数。

建议证据目录：

```text
docs/evidence/<matrix-id>/<device-and-config>/
  environment.json
  steps.md
  web.png
  android.png
  diff.png
  network-redacted.json
  result.md
```

命名中的环境值必须具体，包含设备 / API、App commit、Web commit、服务端版本、宽度、DPR、字体缩放、主题、语言、IME和权限。含私人内容的截图及网络记录只在指定私有存储保留。

## 8. CI 设计

Android 工程与 CI 建立后，涉及应用代码、构建或依赖的 PR：固定 JDK 与 Android SDK → 校验 Wrapper → 编译 → JVM测试 → Lint → Debug APK → 上传测试报告及失败证据。触及协议 / 保存 / 恢复时运行相应集成集合；触及可见界面时提供设备截图；影响编辑器、流式投影或终端性能时，按冻结的 D03 运行对应预算检查。P0独立准备按任务退出条件检查；纯文档 PR 按 `AGENTS.md` 检查链接、锚点、JSON / CSV和事实源一致性，不触发 Android 构建。

主分支和发布候选：增加模拟器仪器测试、全量双端回归集合及 Release构建。真实服务器凭证通过CI秘密注入；不能把开发者电脑或私人数据当CI环境。

PR按变更范围运行必要检查，发布候选运行完整范围。失败必须区分环境故障与产品问题，重试要有原因。构建成功、测试通过、真机通过和发布分别记录。

## 9. 发布候选交付包

交付 APK 与 SHA-256，记录源码 commit、Web基线、服务器版本、构建工具链、签名证书指纹和渠道。附上完整矩阵、测试报告、界面差异、平台差异、运行指南、依赖许可与已知问题。

安装验收：首次安装 → 输入服务器 → 登录 → 三条核心链路 → 退出 / 重启 → 网络恢复 → 更新安装并读取本地草稿。服务端数据继续通过现有协议访问。

发布前核对本项目改动全部属于Android仓库，后端未引入修改。若规划阶段的关键能力尚未通过，交付标为阶段构建，不能标为全量1:1完成。

## 10. 第一轮开发任务与交接示例

新项目的首轮任务是P0与G1，不先铺开所有页面。交接给工程师或开发代理时可使用以下任务卡，并填入真实的项目身份和测试环境。

```text
任务：P0基线冻结与G1连接认证
输入：本包、固定Web提交、测试服务器及版本、测试账号、已确定的应用身份
范围：初始化Kotlin/Compose工程；实现连接、status、登录、pair、Cookie和退出
界面：逐状态对应手机Web认证流程；服务器输入是客户端启动必需的适配入口
实现约束：单app模块；固定工具链；后端代码零改动；本地数据按ServerKey隔离
验证：HTTP/WS与HTTPS/WSS真实往返；图片鉴权；一次性pair；迟到401；退出迟到回包
产出：源码、必要测试、Debug APK、脱敏往返记录、AUTH-001至AUTH-007的验证结果
退出：每个操作有读回结果；未测环境明确标记；未通过G1前不标为连接功能完成
```

第二轮按G2/G3完成可编辑文档与保存冲突，G4/G5并行验证流与终端。每轮只锁定具备证据的依赖，再进入P2公共界面和P3完整写作。

代码审查重点为：本次用户流程是否闭合、作用域和副作用是否准确、失败后输入是否保留、恢复是否重复写入、测试是否覆盖真实风险、页面是否完成双主题与移动输入对照。接口或UI缺少证据时指出具体字段或状态，不以“差不多一致”签收。
